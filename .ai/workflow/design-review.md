# 架构改动自检

定位：架构级改动的强制清单（非正式审批流）。个人 vibe coding 默认清单过完可开工；用户要求确认时再等。

## 何时必须
- 新架构模式、系统/模块边界变化、拆并模块
- 新基础设施、跨切面能力、框架级抽象
- 主技术栈/持久化/通信机制替换
- 核心实体、数据所有权、一致性模型变化

## 何时不必
bug、小 feature、局部重构、测试与文档、无行为清理。

## 清单（按序写短答）
1. **现状**：现在怎么做
2. **问题**：真实限制/需求是什么（不是「以后可能」）
3. **影响面**：谁受影响
4. **现有能力**：为何不够，能否扩展而非新建
5. **方案**：至少两个选项 + 推荐 + 理由
6. **复杂度**：实现/运维/学习/维护成本是否值得
7. **演进**：是否跳级（简单→模块→服务→分布式）
8. **责任边界**：是否清晰，会否制造万能依赖
9. **失败**：如何失败、降级、恢复、怎么观测
10. **文档**：要改哪些 docs；是否需要 ADR

## ADR（重要决策时）
写入 `docs/architecture/adr/`：上下文 / 决策 / 弃选 / 后果。
